# Rewinding live TV

Status: draft for review · Builds on PR #5 (playback buffer and silent
reconnect, branch `feat/playback-buffer`) · Step 2 of
`2026-10-30-buffering.md`, which this spec replaces for Step 2

The viewer can rewind the channel they are watching, jump forward again and
return to live. Pausing keeps working without a second connection to the
server. Rewinding is off by default because of the disk space it uses.

## Decisions from the review

| Question | Answer |
| --- | --- |
| Is rewinding wanted? | Yes, configurable. |
| Default | Off. |
| Disk space | Stop when the disk runs low; the limit is a setting. |
| Pull requests | A separate PR, from `origin/main` once PR #5 is merged. |

## What happens after PR #5

- `StreamProxy` creates one `Session` for each player connection. The
  `Session` belongs to the socket, so it ends when the player disconnects.
  It fetches the stream, feeds a `StreamBuffer` and reconnects on its own.
- When the `StreamBuffer` is full, the session stops reading from the
  server. A paused player stops reading, so the server connection stalls.
- Pausing calls `StreamRecorder::start()`. This opens a **second**
  connection to the server and saves the stream to
  `~/Videos/TV recordings/Paused - ….ts`. Many IPTV accounts allow only
  one connection, so the second one can fail or cut off the first.
- `StreamRecorder` records HLS streams as well. For HLS it saves the
  playlist text, not video, so pause and resume from a file is already
  broken for HLS.

## Behaviour

### Settings

Two new rows go under "Playback buffer":

| Row | Values | Stored as |
| --- | --- | --- |
| **Rewind live TV** | *Off* (default), *15 minutes*, *30 minutes*, *1 hour*, *2 hours* | `playback/rewindMinutes` (0, 15, 30, 60, 120) |
| **Keep free disk space** | *1 GB* (default), *2 GB*, *5 GB*, *10 GB* | `playback/minFreeGb` |

- The Rewind row's description shows the disk use at 8 Mbit/s, for example
  "Uses up to about 1.8 GB".
- "Keep free disk space" applies to rewinding and to pausing. It is shown
  while rewinding is on and hidden otherwise. A pause still uses the stored
  limit.
- Both rows work with Left and Right, like "Playback buffer".

### Keys while watching

| Key | Rewind on | Rewind off |
| --- | --- | --- |
| Rewind | Back 10 s | Nothing |
| Fast Forward | Forward 30 s, never past live | Forward 30 s while behind live after a pause |
| Left / Right while paused | Back 10 s / forward 30 s | Forward 30 s (Right) while behind live |
| Play/Pause, OK | Pause and resume, as today | Pause and resume, as today |

- Left and Right while playing keep their current jobs: channel list and
  guide.
- Presses within 0.6 s add up into one jump, so holding Rewind moves
  smoothly.
- While jumping, a bar at the bottom shows the rewind window, the position
  in it and the time behind live, for example "−2:30". It hides 3 s after
  the last press.
- Jumping forward to live shows "Live", and the behind-live icon
  disappears.
- Rewinding past the oldest data stops at the oldest data.

### What is kept

- Rewinding keeps one channel only. The window starts when the channel
  starts playing, and changing the channel discards it.
- Rewinding works for MPEG-TS streams. That covers TVHeadend's default
  `pass` profile and most IPTV. Other streams, such as a TVHeadend
  Matroska profile, and HLS show "Rewind isn't available for this channel"
  on the first Rewind press. Pausing them is a plain pause (see Pausing).
- While behind live, the existing behind-live icon shows the time behind,
  for example "−2:30".

### Pausing

| Case | What happens |
| --- | --- |
| Rewind on | The player pauses. The channel keeps being written to disk, and resuming continues from the same moment. |
| Rewind off, MPEG-TS | Pausing starts a pause file from that moment. Resuming plays from it, behind live. Fast Forward catches up. Changing the channel or stopping deletes the file. |
| HLS or another format | The player pauses, with no file and no second connection. The existing reconnect handles a server that drops the paused stream. |

The last row is a regression for one case only. A TVHeadend user on a
Matroska profile can resume today from the file `StreamRecorder` saved,
because it starts at the stream's beginning. That file came from a second
connection. See open point 1.

## Design

### Sessions outlive player connections

`StreamProxy` keeps its sessions itself, one for each relay token, instead
of making each one a child of a socket.

- A session owns the server connection, its reconnect logic from PR #5, and
  an optional `TimeshiftBuffer`.
- Player connections attach to a session as **readers**.
  - A **live reader** reads from the session's `StreamBuffer`, as in PR #5.
  - A **file reader** reads from the `TimeshiftBuffer` at a position.
- A session without readers ends after 5 s, unless it is recording. A
  recording session lives until `endSession(token)` is called or a newer
  relay replaces it.
- While a session is recording, it reads from the server as fast as data
  arrives. The live reader's `StreamBuffer` no longer slows down the
  server connection. When that buffer is full, the oldest data in it is
  dropped. A paused player then can't stall the server or the recording.

### Recording to disk

A new class, `TimeshiftBuffer` (`src/timeshiftbuffer.{h,cpp}`), has no
network code, like `StreamBuffer`.

- **Feed:** `StreamBuffer` gains an optional sink. It is called with each
  aligned 188-byte packet and its media time, so the file always holds
  whole packets on one clock that runs across reconnects.
- **Files:** 1-minute chunk files in
  `QStandardPaths::CacheLocation + "/timeshift/<token>/"`, named by number.
  Each chunk keeps an index in memory: media time to file offset, one entry
  per second.
- **Length:** chunks older than the rewind length are deleted. A pause
  file is a buffer with no length limit, limited only by disk space.
- **Disk:** before each new chunk, `QStorageInfo` checks the free space.
  If it is below "Keep free disk space" plus one chunk at the measured byte
  rate, writing stops. The notice reads "Rewinding stopped: the disk is
  nearly full". Playback continues live, and what was already written can
  still be rewound. The free-space check is a function that tests can
  replace.
- **Clean-up:** on start, any `timeshift/` folders left by a crash are
  deleted. The old `Paused - *.ts` files in `~/Videos/TV recordings` are
  still cleaned up for one release, then that code goes.

### Playing from the past

- The relay address takes `?behind=<ms>`. A file reader starts at the
  index entry nearest to "newest media time − behind", then follows the
  file as it grows across chunk boundaries. No offset means live.
- Qt Multimedia can't seek in a live stream. A jump therefore means
  `PlayerView` sets a new source address with the new `behind`.
- A file reader uses the Step 1 rules (Auto growing after stalls). They
  are measured as the media time between the reader and the newest data, so
  a reader that catches up with live behaves like a live reader.

### Who calls what

`TvhBackend` remembers the relay token of the playing channel and gains:

| Call | Does |
| --- | --- |
| `requestStream(uuid)` | As today. It also starts recording when rewind is on and the stream is MPEG-TS. It ends the previous channel's session. |
| `Q_INVOKABLE bool holdStream()` | Starts a pause file for the current session, if rewind is off. False for HLS and other formats, and PlayerView then pauses plainly. |
| `Q_INVOKABLE QUrl timeshiftUrl(double behindMs)` | The relay address with `?behind=`. |
| `Q_INVOKABLE void stopStream()` | Ends the session and deletes its files. Called by `PlayerView.stop()` and on a channel change. |
| `Q_PROPERTY rewindAvailable`, `rewindWindowMs` | For the keys and the bar. |

### PlayerView and WatchOverlay

- `PlayerView` keeps `paused` and `timeshifting`. `timeshifting` now means
  `behindMs > 0`. It gains `behindMs`, worked out from the `behind` the
  current source started at plus the time spent paused, and
  `jump(deltaMs)`.
- `togglePause()`:
  - Rewind on: pause and resume the player.
  - Rewind off: `holdStream()` on pause. On resume, play from
    `timeshiftUrl(pause length)`.
- `WatchOverlay` handles Rewind and Fast Forward, Left and Right while
  paused, the 0.6 s grouping of presses and the position bar.
- `StreamRecorder` is removed. `qml/PlayerView.qml` no longer creates it.

## Tests

| Test | Covers |
| --- | --- |
| `test_timeshiftbuffer` (new) | Writing packets and rotating chunks; deleting by length; finding the position for `behind`; a reader following the file across chunks; stopping on low disk (replaced free-space check); clean-up of leftovers |
| `test_streambuffer` (extended) | The packet sink gets every aligned packet with a continuous media time, also across `cutForReconnect()`; dropping the oldest data when full while recording |
| `test_streamproxy` (extended) | A recording session survives the player disconnecting; `?behind=` serves older data; the server connection keeps going while a live reader doesn't read; `endSession` deletes the files; a session without readers ends after its grace time |
| `test_appsettings`-like checks | Clamping `rewindMinutes` and `minFreeGb`, if done in a testable helper |

The keys, the bar and real playback need a check on a Bigscreen device:
- rewind and jump forward on a TVHeadend channel and an M3U channel;
- pause with rewind off and on;
- a Matroska profile and an HLS channel showing the "not available"
  notice.

## Out of scope

- Rewinding HLS or non-TS streams.
- Keeping the rewind window across channel changes or restarts.
- Saving a stretch of the rewind window as a recording. That belongs to the
  recording feature.
- Trick play: smooth fast-forward at 2× or 4×.

## Open points for you

1. **Matroska and other non-TS streams:** pausing would become a plain
   pause, with no resume from a file. Is that acceptable? The other option
   is to keep `StreamRecorder`'s separate download for those streams only,
   which needs a second connection.
2. **Jump sizes:** 10 s back and 30 s forward. Do you want different
   values?
3. **Back to live:** Fast Forward until live is the only way back. Should
   another key, such as Stop, also jump to live? Today Stop leaves the
   player.
